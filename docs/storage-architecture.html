The snapshot boundary — what the run could see, fingerprinted

The snapshot boundary. ingest (write) and run (read) are separate phases. snapshot_id = SHA-256 over every reading with as_of ≤ D in canonical order — it fingerprints exactly the store state the run could see, and a later disclosure (as_of > D) can never move it. This boundary, plus a wall-clock-free generated_at, is what makes dashboard.json reproduce byte-for-byte.

02Medallion tiering — where every byte lives

A single conceptual log, physically split across four media. Callers only ever touch the PointInTimeStore Protocol — tiering, Parquet, and the replica are all invisible behind it.

🟦 SILVER · hot store — DuckDBStore, out/store.duckdb

  • One DuckDB file, one readings table, one connection per instance (not pooled, not a singleton).
  • One writer or many readers — DuckDB's hard rule; bridged by the replica (§06).
  • :memory: default → ephemeral; run auto-populates it standalone. A real path → durable, ingest fills it.
  • No PRAGMAs on the writer; the only tuning is on replica connections.

🟦 COLD · Parquet tier — cold_dir/series=…/year=…/*.parquet

  • After each ingest, tier_cold(cutoff) moves rows with as_of < cutoff out of the hot table to Hive-partitioned Parquet via DuckDB COPY … (FORMAT PARQUET, PARTITION_BY (series, year), APPEND).
  • Bounds the hot file as years of history accrue.
  • _readings() transparently UNION ALLs hot rows with read_parquet(glob, hive_partitioning=true) — reads are unchanged, snapshot stays identical.
  • None → whole log stays hot (default).

🟪 GRAPH · LadybugDB — out/graph.ladybug

  • Embedded on-disk openCypher graph DB (not the daylighting library — it's ladybugdb.com).
  • Schema: Fund(code PK), Security(code PK), HOLDS rel with weight, as_of, source, valid_from, valid_to.
  • Point-in-time via half-open [valid_from, valid_to) windows on edges.
  • Built from store.history("fund_holdings"|"edgar"); powers look-through connections.

🟨 GOLD · derived JSON — out/dashboards/, out/series/

  • Not DuckDB at all — flat per-file JSON, atomically written (stage file + os.replace).
  • Immutable per-night dashboards + a materialized index.json catalog (a cache, never the source of truth).
  • Append-only per-fund NAV/factor trails — first point per as_of stands.
  • This is what serve.py reads; the store is never exposed over HTTP.

03The Reading — the one fact, and the one table

Every fact in the system is a Reading: a stamped, append-only row. series is the logical table, key the entity, as_of the disclosure date (point-in-time), fetched_at when it was pulled (never the artifact's clock), payload the values (schema-on-read JSON).

Python model store/__init__.py:32–41

    """One stamped, append-only fact in the store."""
    model_config = ConfigDict(frozen=True)   # immutable

    series: str       # source/table: "prices","fred"…
    key: str          # entity within series: fund code…
    as_of: str        # ISO date the fact was true (PIT)
    fetched_at: str   # ISO ts pulled — never the clock
    payload: dict[str, Any]  # the row's values

Series seen in the wild: positions · prices · fund_universe · etf_scale · fund_holdings · fundamentals · trading_activity · fred · edgar · demand · themes · theme_map · textstream · calls · debate_cache

DuckDB schema store/__init__.py:71–80

CREATE TABLE IF NOT EXISTS readings (
    series     VARCHAR NOT NULL,
    key        VARCHAR NOT NULL,
    as_of      VARCHAR NOT NULL,
    fetched_at VARCHAR NOT NULL,
    payload    VARCHAR NOT NULL,   # json.dumps(sort_keys)
    PRIMARY KEY (series, key, as_of, fetched_at)
);
  • Exactly one table, one composite PK, no secondary indexes, no FKs, no persisted views.
  • payload is canonical sorted-key JSON text → deterministic serialization & hashing.
  • The cold "view" is an ad-hoc SQL string in _readings(), not a DuckDB VIEW object.

05The two guarantees: append-only & point-in-time

Write side — content-addressed revisions append() :130

# write only if payload DIFFERS from the latest
# revision held for (series, key, as_of)
INSERT INTO readings (...)
SELECT i.* FROM _incoming i
LEFT JOIN (
  SELECT series,key,as_of,payload FROM readings
  QUALIFY row_number() OVER (
    PARTITION BY series,key,as_of
    ORDER BY fetched_at DESC) = 1
) latest USING (series,key,as_of)
WHERE latest.payload IS NULL
   OR latest.payload <> i.payload
ON CONFLICT DO NOTHING
  • Nightly re-pulls the full history; an unchanged bar arriving again under a fresh fetched_at writes zero rows (dedup is on content, not the fetch stamp — cross-night, not just within a run).
  • A genuine restatement (changed payload, same as_of) lands as a new revision — the old row is never edited.
  • No UPDATE/DELETE anywhere except the physical relocation inside tier_cold.

Read side — point-in-time selection read_as_of() :176

SELECT series,key,as_of,fetched_at,payload
FROM {hot ∪ cold}
WHERE series = ? AND as_of <= ?
QUALIFY row_number() OVER (
  PARTITION BY key
  ORDER BY as_of DESC, fetched_at DESC) = 1
ORDER BY key
First write wins / no rewriting history. A future disclosure (as_of > D) is excluded by the WHERE before the window even runs — it structurally cannot influence a past-dated read, regardless of when the row was inserted. Among same-as_of revisions, latest fetched_at wins.

Reasoning sees only what was knowable as-of the run date — enforced by the query, not by discipline. Verified by test_a_later_disclosure_does_not_rewrite_history.

Invalid inputs degrade, never raise. A stale/short/missing reading becomes a FactorState(valid=False) (band neutral, "missing ≠ bad") and is kept, not dropped. The trend gate is the one hard cap: below the 200-day MA → GateState.CAPPED, and nothing — not even an overconfident model — may open a capped gate.

06Read replica — bridging "one writer or many readers"

DuckDB allows one read-write or many read-only handles per file. The nightly writer holds the live store RW, so ad-hoc queries can't open it. Solution: after the run closes the writer, publish a separate read-only file replica.

publish_replica() replica.py:29

publish_replica(store_path, replica_path) → Path

  • Copies the hot file to <name>.staging, then os.replace() for atomicity — a concurrent reader never sees a half-written replica.
  • Only the hot DuckDB file is copied; cold Parquet is queried in place.
  • Called by nightly() right after the writer is closed & checkpointed.

ReadReplica pool replica.py:50

ReadReplica(path, pool_size=4, memory_limit="256MB", row_limit=10_000, timeout_s=5.0)

  • Opens N read-only connections up front; each bounded by SET memory_limit (the only PRAGMA tuning in the layer).
  • query(sql, params) checks a connection out of a queue.Queue (blocks → bounds concurrency).
  • Per-query caps: fetchmany(row_limit), worker thread + join(timeout) → con.interrupt() raising QueryTimeout. One heavy query can't starve the box.

08Gold artifacts & the serve layer

history.py — immutable per-night

  • record(dash, dir) → Path writes <as_of>.json; if path.exists(): return path — first write wins, a later run never rewrites a night.
  • Same Dashboard object is also written to out/dashboard.json (always overwritten = "latest") — verified byte-identical content (same snapshot_id).
  • index.json catalog maintained at write time (_catalog_night, dict.setdefault); a missing/corrupt catalog degrades to _rebuild_index() globbing *.json — never an error.
  • All writes atomic: staging file + os.replace.

series.py — per-fund gold trail

  • Reads only store.read_as_of("prices", as_of) for NAV; not DuckDB-backed itself.
  • materialize() → list[SeriesEntry] = (code, name, SeriesPoint).
  • record() appends a point per fund; first point per as_of stands, mirroring the append-only store. Atomic rewrite per fund file.
  • list_codes() globs the dir live for the /series catalog (no index file).

09Theme discovery — the research-side data pipeline

The store has a second writer. Apart from the nightly ingest, a separate discover job (weekly by convention) turns a rolling Chinese-language text stream into candidate themes Readings. It runs the engine's only heavy data-processing stack — sentence embeddings, an online topic model, and a cost-stratified LLM — entirely on the host (a Mac mini; no paid topic-model API), on the research side of the snapshot boundary: it only appends dated Readings, so the nightly's deterministic reasoning is untouched. The next ingest maps the discovered themes to funds; run surfaces them in the emerging list.

A @runtime_checkable Protocol: discover(docs, *, as_of) → list[TopicTrajectory].

12Determinism & the offline switch

No wall clock in the artifact path

  • Fixtures fetched_at_for(as_of) = f"{as_of}T22:00:00Z" ingest/base.py:21.
  • Dashboard.generated_at = f"{as_of}T22:00:00Z" pipeline.py:821 — identical pattern.
  • Wall-clock time appears only in ops telemetry (run log / spend ledger), never in dashboard.json.
  • Result: dashboard.json reproduces byte-for-byte; a second ingest over an unchanged snapshot writes ~0 rows.

Online by default; offline is the test mode

  • FACTOR_SCOPE_OFFLINE=1 (or --offline) flips source→fixtures & provider→fake (incl. the discovery fakes).
  • get_feed(config) returns LiveFeed vs CassetteFeed(fixtures/cassettes).
  • tests/conftest.py sets the env var at import time, before config is imported — so the whole suite + CI are hermetic and deterministic, preserved by the snapshot boundary + mocks, not by avoiding the network.
